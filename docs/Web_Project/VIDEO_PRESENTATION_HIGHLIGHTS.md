## 1. 「よく使う食品・活動」管理画面におけるUI/UXの工夫（[`FoodMasterView.tsx`](../../src/components/foods/FoodMasterView.tsx) / [`FoodCard.tsx`](../../src/components/foods/FoodCard.tsx)）

### ① 「カード型」ではなく「リスト型（1行完結・縦並び）」を採用した理由
- **視線移動の最小化（Z字移動から垂直スキャンへ）**:
  - 写真が主役のECサイト等とは異なり、本画面は「カテゴリ・名称・基準量・糖質量（または実施時間）」という**定型テキストと数値を素早く検索・比較する画面**です。
  - カード型（2〜4列グリッド）では視線が左上から右下へジグザグ（Z字）に飛びますが、リスト型にすることで「食品名（左）」「基準量（中）」「糖質量（右）」が縦一列に揃い、**視線を上下に滑らせるだけで糖質量を0.5秒で比較**できます。
- **「引き算の法則」による重複ラベル・小ボタンの排除**:
  - カード型では全45件のカードに毎回「基準分量:」「糖質量」という同じラベルと `[✎][🗑]` アイコンが45回繰り返され、視覚的ノイズになっていました。
  - リスト型では上部ヘッダーに1回だけ項目名を示すことで重複ラベルを全廃し、1画面あたりの一覧件数を **約2.5倍（スマホでも6件→14件以上）** に高め、スクロール量を半減させました。

### ② 行クリック／タップによるダイレクト編集と一括操作
- **行全体をタップ領域にしたダイレクト編集**:
  - 各行の右端に小さな編集ボタンを置く代わりに、**行のどこをクリック／タップしても直接編集モーダル（[`FoodEditModal.tsx`](../../src/components/foods/FoodEditModal.tsx) / [`EventEditModal.tsx`](../../src/components/foods/EventEditModal.tsx)）が開く設計**とし、スマートフォンでの操作性を大幅に向上させました（単体削除ボタンは編集モーダル内に併設）。
- **チェックボックス複数選択による「一括カテゴリ変更」「まとめて削除」**:
  - 行左端のチェックボックスで複数の食品・活動を選択すると、上部にコンテキスト操作バーが出現し、**1トランザクションでの「一括カテゴリ移動」および「一括削除」** が可能です。
- **PC右サイド「カテゴリメニュー」と列ヘッダークリックソート**:
  - PC画面では2カラム構成を採用し、右サイドメニュー（スクロール追従）に「カテゴリ一覧（件数バッジ付き）＋カテゴリ編集」を常時配置。スマホ画面では縦領域を圧迫しない横スクロールピルに自動切替します。
  - リスト見出し（`食品名 ↕` / `糖質量 ↕` / `標準時間 ↕`）をクリックするだけで直感的に昇順・降順を切り替えられます。

## 2. カテゴリ削除の自由度と「未分類」受け皿設計によるデータ保護（[`CategoryManageModal.tsx`](../../src/components/foods/CategoryManageModal.tsx) / [`foodSeed.ts`](../../src/lib/foodSeed.ts)）

- **なぜ「未分類」カテゴリだけを削除保護（`is_protected: true`）にしたのか**:
  - 初期カテゴリ（主食・主菜・副菜・調味料など）まですべて削除禁止にしてしまうと、ユーザーが自分の食生活に合わせてカテゴリを整理・削除できません。
  - 一方で、カテゴリを削除した際に所属していた食品まで消えてしまったり、存在しないカテゴリIDを持った「迷子データ（どのカテゴリでも絞り込めない孤児レコード）」になったりするのを防ぐ必要があります。
- **削除時の自動付け替えトランザクション**:
  - 本アプリでは **「未分類」のみを削除不可のセーフティネット（受け皿）として保護** し、他のすべてのカテゴリは自由に削除可能としました。
  - カテゴリを削除すると、確認ダイアログで通知した上で、**そのカテゴリに属していた全食品・活動を同一トランザクション内で自動的に「未分類」へ安全に移動**させます。これにより「カスタマイズの自由度」と「参照整合性の100%保証」を両立しています。

## 3. 実測血糖値データ（79,479件）× 臨床リアリティ × ポートフォリオ非永続化設計（[`realGlucoseLoader.ts`](../../src/lib/realGlucoseLoader.ts)）

### ① 実測CGM波形と完全同期した食事・インスリン記録
- **サイン波の架空デモデータを廃止し、約2年分の実測リブレデータ（[`public/data/real_glucose_readings.json`](../../public/data/real_glucose_readings.json)）を採用**:
  - 1日3食（朝食・昼食・夕食）に加え、週末（土日）のみランダムで間食・夜食を記録。
  - **糖質制限（基本100g以内）と高血糖スパイク時の規定超過（最大1.5倍）**: 実測の血糖曲線の「食前の谷」と「食後30〜180分のピーク」を解析し、通常時は糖質100g以内の献立、食後に急激な高血糖スパイクが起きている箇所では規定量の1.15〜1.4倍（天丼セットや大盛ラーメン＆餃子など）を割り当て、**グラフの波形と食事内容の因果関係が100%一致**します。
  - **食べ合わせ規約と理論値計算**: 主食の重複（ごはん＋パン等）や不自然な組み合わせ（パン＋みそ汁等）をプログラムと単体テスト（[`dataIntegrity.test.ts`](../../src/lib/__tests__/dataIntegrity.test.ts)）で排除し、インスリン単位数も日本食品標準成分表の糖質量と食前血糖値（カーボカウント理論 ICR + ISF補正）から算出しています。

### ② ポートフォリオ公開モード（非永続化）と個人本番モードの100%コード共有
- **採用担当者がすべてのCRUD操作を安心して試せる「セッション限定動作」**:
  - ポートフォリオ環境（`VITE_APP_MODE=portfolio`）では、閲覧者が食事記録・食品追加・一括削除・カテゴリ削除・目標閾値変更をすべてインタラクティブに試せます。
  - 同時に、他者の閲覧環境を汚さないよう、**ブラウザを再読み込み（F5）すると変更を永続保存せずクリーンな初期状態へ自動リセット**される設計（本番環境と100%同一コードベース）を実現しています。

## 4. データ分析画面における「旧VBA準拠マルチグラフ統合」「約3秒→0.01秒以下の高速化」「医療安全・情報設計」（[`AnalysisView.tsx`](../../src/components/analysis/AnalysisView.tsx) / [`analysisCalculators.ts`](../../src/lib/analysisCalculators.ts)）

### ① タブ切り替えの分断を排した「1画面マルチグラフ統合ダッシュボード」
- **引き算の法則によるタブ廃止と、データの特性に合わせた最適なレイアウト配分**:
  - グラフごとにタブを分けてしまうと「複数のグラフを同時に見比べて因果関係を探る」ことができず、2段ナビゲーションで操作も煩雑になります。そこでタブ切り替えを廃止し、旧VBAの分析シートと同様に1画面で全4分析を俯瞰できる構成に一本化しました。
  - **上段（2カラム並列・高さ完全一致）**: 左上に最も利用頻度の高い **①食品別の血糖変化（カテゴリ絞り込み連動セレクトボックス付き）**、右上に **②曜日別の傾向** を同じ高さで並列配置し、視線を左右に動かすだけで「特定の食品の影響」と「曜日の生活リズム」を比較できます。
  - **中段（左：集計テーブル ／ 右：横棒グラフ）**: **③時間帯別の傾向（4区分）** は旧VBAと同様に左側に集計表、右側に横棒グラフを配置し、数値と視覚的比率を同時に把握できます。
  - **下段（2カラム分のフル幅）**: **④日次 糖質・インスリン推移** は90日や全期間など広い期間を選択してもグラフが潰れないよう2カラム分のフル幅で表示し、さらに「全期間」選択時は実データの最古記録日〜最新記録日を自動検出して空白期間による平均値の希釈を防いでいます。
- **日常用語への統一（「併食」→「一緒に食べたもの」）と行クリックアコーディオン**:
  - 聞き慣れない「併食（供食）」という専門用語を廃止し、誰にでも直感的に伝わる **「一緒に食べたもの（`＋他2品`）」** という日常表現に統一しました。また、各行をクリックしたときだけ副菜リストが展開されるアコーディオン方式により、全件表示の一覧性とスッキリした視認性を両立しています。

### ② 医療安全（低血糖リスク防止）の観点による「曜日別 平均インスリン量」の除外（[`WeekdayTrendsTab.tsx`](../../src/components/analysis/WeekdayTrendsTab.tsx)）
- **単なるデータ羅列ではなく、患者の行動リスクまで考慮したグラフ設計**:
  - 曜日別グラフに「平均インスリン量（U）」を糖質量（200〜300g）と並べて表示すると、数値のスケール差で変化が潰れてデータの価値が低いだけでなく、**「特定の曜日の平均血糖値が高いのは、その曜日の平均インスリン量が少ないから多めに打てばよいのでは？」という誤った自己判断（過剰投与による重篤な低血糖リスク）** を誘発する危険があります。
  - インスリン量は曜日の平均ではなく「その日の食事の糖質量と食前血糖値」に応じて決まるべきものであるため、曜日別分析ではあえて平均インスリン量を除外し、**「生活リズム（外食・間食）による糖質摂取量の変化と血糖値の相関」** にフォーカスする安全な情報設計としました。

### ③ 79,479件の集計待ち時間を「約3秒 → 0.01秒以下（体感ゼロ）」にした3段階の最適化
- **課題**: ローカルDB（IndexedDB）にデータがあっても、期間やグラフを切り替えるたびに7.9万件の全件フィルタリングと多重ループ計算（`O(N × M)`、最大約5,800万回の比較演算）が走ると、毎回約3秒のローディング待ちが発生していました。
- **解決アプローチ**:
  1. **単一パス（`O(N + M)`）日付インデックス化**:
     - 全79,479件の血糖データと全イベントを日付（`YYYY-MM-DD`）ごとの `Map` に1回だけインデックス化することで、日次推移集計や食前・食後ピーク探索の計算量を **数千万回 → 数百回（約1,000倍以上高速化）** に削減しました。
  2. **食事インパクト探索の局所ウィンドウ化**:
     - 各食事の「食前15分〜食後180分」の血糖値を探す際、7.9万件全体を走査する代わりに、日付インデックスから「食事当日と前後日」のデータ（最大約200件）だけを参照するアルゴリズムに刷新しました。
  3. **オンメモリ・データセット＆期間別集計キャッシュ**:
     - 一度読み込んだデータおよび期間別（直近7日・14日・30日・90日・最新月・全期間）の集計結果をメモリ上にキャッシュし、**期間やカテゴリ・食品を切り替えた際の再アクセス・ローディングスピナーを完全にゼロ（0ms即時反映）** にしました（※食事・活動の追加や削除、目標閾値の変更が行われた場合はシグネチャ検知により自動でキャッシュを更新します）。

## 5. 医療データ品質を担保する「4層テスト設計」「開発フェーズ別テストスケジュール」「AIによる自動化の工夫」（[`TEST_PLAN.md`](./TEST_PLAN.md) / [`e2e/app.spec.ts`](../../e2e/app.spec.ts) / [`deploy-pages.yml`](../../.github/workflows/deploy-pages.yml)）

医療・健康管理アプリでは「1箇所の計算ミスや画面間の数値不一致が重大な判断ミスにつながる」ため、単なる画面表示確認にとどまらない**多層的な自動テスト体系**を構築しました。

### ① 4層の自動テストピラミッド（何を守るテストか）
1. **Layer 1: 仕様書同期・セキュリティ・UI用語の自動監査ゲート（[`scripts/verify-docs-sync.mjs`](../../scripts/verify-docs-sync.mjs) / `npm run test:docs`）**
   - **仕様書とコードの乖離ゼロ強制**: ソースコード（`src/components/**`, `src/lib/**`）を変更した際、対応する仕様書（`SPEC_*.md`）が同一変更セット内で更新されていなければエラーとして検出します。
   - **セキュリティ・アンチハリボテ・ユーザー目線用語の機械的検査**: 全46ソースファイルを走査し、「APIキーを `localStorage` に保存する危険なコードがないか」「機能しないダミーボタン（ハリボテUI）がないか」「画面上に『マスタ』『IndexedDB』『Web Worker』などの開発者用語が露出していないか」を自動検査します。
2. **Layer 2: 臨床計算アルゴリズム＆画面間データ整合性の単体・統合テスト（[`analysisCalculators.test.ts`](../../src/lib/__tests__/analysisCalculators.test.ts) / [`dataIntegrity.test.ts`](../../src/lib/__tests__/dataIntegrity.test.ts) / [`gemini.test.ts`](../../src/lib/__tests__/gemini.test.ts) / 全28件）**
   - **医療計算ロジックの厳密検証**: 15分ルールに基づく異常値エピソード抽出ステートマシン、食前15分〜食後180分のピーク探索と血糖上昇幅（$\Delta$）、4時間帯集計、79,479件実測データの食べ合わせ整合性、および「設定画面の目標閾値変更 $\rightarrow$ カレンダー・日次詳細・分析画面の再計算連動」を Vitest でミリ秒単位で検証しています。
3. **Layer 3: 開発サーバー・ランタイムスモークテスト（[`scripts/smoke-test.mjs`](../../scripts/smoke-test.mjs) / `npm run test:smoke`）**
   - 静的ビルド（`tsc`）が通っても、Vite開発サーバーのモジュール解決エラーやキャッシュ起因の画面クラッシュが発生しないことを、全28コンポーネントエンドポイントへのHTTP 200応答＆エラーパターンゼロ検証で保証しています。
4. **Layer 4: Playwright による実ブラウザ E2E リグレッションスイート（[`e2e/app.spec.ts`](../../e2e/app.spec.ts) / 全9スイート）**
   - 実際の Chromium ブラウザ上で以下の9大シナリオを一気通貫で自動検証します：
     - **`E2E-1`（表示速度SLA & ポートフォリオ自動リセット）**: 初期カレンダー集計・描画が **2,000ms以内（実測約570ms）** に完了すること、およびデータ追加後にF5リロードすると初期状態へクリーンリセットされること。
     - **`E2E-2`（マスタ登録・カテゴリ削除救済・記録画面連動）**: よく使う食品（糖質自動推定含む）・活動の登録、カテゴリ削除時の「未分類」への自動移動（孤児データ防止）、および食事・活動記録モーダルの選択肢への即時反映。
     - **`E2E-3`（画面上の計算ロジック & 3画面数値完全一致）**: 食品の分量倍率変更（例: ごはん1.5杯＝82.8g）による比例計算、合計糖質・インスリン量、食前→食後ピーク（$+\Delta$）の整合性、および**「上部サマリーバー」「カレンダー日付セル」「日次詳細パネル」の3箇所の数値が100%一致**すること。
     - **`E2E-4`（目標閾値変更による異常値ステートマシン再計算 & デフォルトインスリン連動）**: 設定画面で高血糖閾値を `180` $\rightarrow$ `140 mg/dL` に引き下げて保存すると全期間の異常値回数が即座に再計算されて増加し、食事区分別デフォルトインスリン単位数も新規記録モーダルへ連動すること。
     - **`E2E-5`（4大分析ダッシュボード集計 & スマホ横スクロールゼロ検証）**: TIR（目標範囲内時間）の3区分合計が100%になること、およびスマートフォン幅（`375px`）で横スクロールはみ出し（レイアウト崩れ）がゼロであること。
     - **`E2E-6`（見守り家族ロール `isReadOnly` の完全操作ロック）**: ロール切替時に全画面の追加・編集・削除・CSV取込・設定保存が物理的にロックされること。
     - **`E2E-7`（異常系・境界値バリデーション & 破壊的操作ガード・論理削除減算）**: 食品0品時の保存ブロック、インスリン未入力時の0単位確認ダイアログ、入力途中の「変更破棄確認ガード」、および食事削除時の合計糖質即時減算。
     - **`E2E-8`（大容量CSV Web Worker 並列取込 & JSONバックアップ・復元ラウンドトリップ）**: リブレCSV取込の非同期完了と、JSONバックアップ出力 $\rightarrow$ 初期状態リセット $\rightarrow$ JSON復元による完全復元。
     - **`E2E-9`（完全オフライン動作 & 内蔵食品辞書フォールバック）**: ネットワーク切断（`context.setOffline(true)`）時のオフラインバナー表示、全タブ画面のエラーゼロ遷移、およびオフライン下での内蔵日本食品標準成分辞書による糖質自動推論。

### ② 開発中のテスト実行スケジュール設計（速度と網羅性の両立）

| 実行タイミング | 実行コマンド / 仕組み | 所要時間 | 検証の目的・スコープ |
| :--- | :--- | :---: | :--- |
| **1. 実装中（機能単位・随時）** | `npm test` / `npm run typecheck` | **約2〜5秒** | 仕様書（DoD）に基づく臨床計算ロジック（ステートマシン・糖質計算・タイムゾーン処理）と型の即時フィードバック |
| **2. Gitコミット時（毎回自動）** | `.git/hooks/pre-commit`<br>（`npm run test:docs` + `typecheck`） | **約5秒** | 仕様書の更新漏れ、APIキー平文保存、ハリボテUI、開発者用語の露出、型エラーを**コミット入口で100%自動ブロック** |
| **3. PR作成・機能統合時** | `npm run verify:all` + `npm run test:smoke` | **約15〜20秒** | 単体テスト全28件＋本番バンドルビルド＋Vite開発サーバー全28モジュールのHTTP 200ランタイム健全性検証 |

### ③ AIによるテスト自動化の工夫と「E2Eによる潜在バグの自己発見・自己修復」
本プロジェクトでは、AIコーディングエージェント（Antigravity）の推進力を最大限に活かしつつ、**「AIが陥りやすい品質低下や推測実装をAI自身の仕組みで防ぐ」** ための工夫を取り入れました。

1. **「仕様書ファースト（DDD）」とAI自律品質ゲートの組み込み（[`AGENTS.md`](../../.agents/AGENTS.md)）**:
   - AIにいきなりコードを書かせるのではなく、必ず「①4軸評価（セキュリティ・拡張性・保守性・ユーザビリティ）と仕様書（`SPEC_*.md`）の定義 $\rightarrow$ ②テスト設計 $\rightarrow$ ③実装 $\rightarrow$ ④自動ゲート検証」の順序をシステムルールとして強制しました。
   - 特に、人間やAIが見落としがちな「ローカル時刻とUTCの9時間ズレ防止規約」や「開発者目線ワード（『マスタ』等）のUI露出禁止」を [`verify-docs-sync.mjs`](../../scripts/verify-docs-sync.mjs) でコード検査ルール化し、**AIが自分で書いたコードを自分で監査・修正する自律ループ**を構築しました。
2. **「Zero-Error Policy」と「Anti-Flakiness（不安定さ排除）」の徹底**:
   - E2Eテストでは画面上の見た目だけでなく、裏側で `pageerror`（未キャッチ例外）や `console.error` が1件でも出力されたら即座にテストをFailさせる **Zero-Error Policy** を全テスト共通の `beforeEach` / `afterEach` ガードとして実装しました。
   - また、固定秒数待機（`waitForTimeout`）を禁止し、ブラウザの `Performance API`（User Timing マーク `cgm-calendar-fetch-start` 〜 `cgm-calendar-data-ready`）や遅延チャンクのプリフェッチ完了属性（`data-chunks-warmed="true"`）を用いた**決定論的な待機設計**としました。
3. **E2E自動テストが実際に発見・解決した「単体テストでは見抜けない3つの潜在バグ」**:
   - **発見①：初期表示直後のバックグラウンド同期（7.6万件）とユーザー保存操作の IndexedDB ロック競合**
     - カレンダーを0.5秒で即座に表示した裏で過去2年分のデータをIndexedDBへ一括投入していたため、画面表示直後に食事を保存したり設定閾値を変更したりすると、IndexedDBの書き込みロック競合で反映が数秒遅れる現象を `E2E-1` / `E2E-4` が検出しました。
     - **解決**: 過去データの投入を1,500〜4,000件ずつの小分けチャンクに分割し、ユーザーがモーダルを開いたり保存したりした瞬間はバックグラウンド同期を自動的に一時ポーズ（[`pauseBackgroundHydration`](../../src/lib/realGlucoseLoader.ts)）する協調制御を実装し、待ち時間をゼロにしました。
   - **発見②：オフライン移行後の遅延ロード（Lazy Chunk）取得エラー**
     - 初期バンドル軽量化のために別画面やモーダルを `React.lazy()` で分割していた結果、一度も開いていないタブへオフライン切断後に移動するとチャンク取得エラーになる問題を `E2E-9` が検出しました。
     - **解決**: カレンダー初期描画完了の200ms後に、アイドル時間を使って全遅延チャンクをバックグラウンドでプリフェッチ（ウォームアップ）する仕組みを [`App.tsx`](../../src/App.tsx) に実装し、初回アクセス直後に機内モード（オフライン）になっても全機能が完全動作するように改善しました。
   - **発見③：約8万件JSONバックアップ出力時の Chrome `data:` URI 2MB上限突破**
     - 設定画面のフルバックアップ出力で `data:text/json` URI を使っていたため、約8万件の実測データ出力時にブラウザのURI長上限（2MB）を超えてダウンロードが失敗する現象を `E2E-8` が検出し、`Blob` + `URL.createObjectURL` 方式へ刷新して解決しました。
